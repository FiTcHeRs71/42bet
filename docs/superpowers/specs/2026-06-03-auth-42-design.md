# Spec — Brique Auth 42 (OAuth NextAuth v5)

> Statut : design validé, prêt pour plan d'implémentation.
> Date : 2026-06-03.
> Contexte : 42Bet, pré-MVP. Verrou du MVP — identifie les users (login, photo,
> ft_id), peuple `public.users`, et débloque paris + classement.

## 1. Objectif

Permettre à un étudiant 42 de se connecter via OAuth2 intra.42.fr, créer/mettre à
jour sa fiche dans `public.users`, et exposer une session persistante côté web.
Cette brique est volontairement **étroite** :

- **Inclus** : login OAuth 42, récupération `login`/`avatar`/`ft_id` depuis `/v2/me`,
  upsert `public.users`, session NextAuth, header avec bouton connexion/déconnexion.
- **Exclu (déféré)** : coalition (`coalition_id` reste `null`), protection de routes
  (middleware), pages paris/classement.

## 2. Décisions de cadrage (validées)

| Décision | Choix | Raison |
|---|---|---|
| Version NextAuth | **v5 (Auth.js, `next-auth@beta`)** | Native App Router / Next 16 ; AGENTS « dernière ». |
| Coalition | **Déférée** (`coalition_id = null`) | `/v2/me` ne la donne pas ; table `coalitions` vide. Brique séparée plus tard. |
| Surface UI | **Header minimal + bouton** | Prouve l'auth de bout en bout sans sur-construire. |
| Échec d'upsert | **Bloque le login** | Les paris ont une FK vers `users` : pas de user fantôme. |

## 3. Architecture

Séparation **logique pure (testable)** / **plomberie NextAuth (intégration)**,
en réutilisant le pattern DI déjà en place dans `src/lib/sync.ts`.

| Fichier | Rôle | Testé |
|---|---|---|
| `src/lib/auth/profile.ts` | **Pur** : `mapFt42Profile(raw: Ft42Me): PlayerProfile` → `{ ftId, login, avatarUrl }`. Gère avatar absent/null. | ✅ unit |
| `src/lib/auth/upsert-player.ts` | **I/O via DI** : `upsertPlayer(profile, deps: UpsertDeps): Promise<void>` → upsert `public.users` on conflict `ft_id`. | ✅ fake DI |
| `src/lib/auth/config.ts` | Plomberie NextAuth v5 : provider `42-school` (built-in) + `profile()` overridé + callbacks. Exporte `handlers, auth, signIn, signOut`. | build/typecheck |
| `src/lib/auth/types.ts` | Augmentation de module : `Session` / `JWT` étendus avec `ftId, login, avatarUrl`. | — |
| `src/app/api/auth/[...nextauth]/route.ts` | `export const { GET, POST } = handlers`. | — |
| `src/components/site-header.tsx` | Server component : lit `await auth()`, rend le header + `<AuthButton/>`. | — |
| `src/components/auth-button.tsx` | Bouton « Se connecter avec 42 » / avatar+login+déconnexion via server actions `signIn("42")` / `signOut()`. | — |

Modifs :
- `src/app/layout.tsx` : inclut `<SiteHeader/>`, titre/description corrigés (plus « Create Next App »).
- `src/app/page.tsx` : remplace le placeholder Next par un accueil sobre (titre 42Bet + état de session).

**Pas de nouvelle migration.** `public.users` a déjà `ft_id` (unique), `login`,
`avatar_url`, `coalition_id` (nullable), `total_points` (default 0), et les grants
service_role (migration 0007). L'upsert se fait `on conflict (ft_id) do update`.

## 4. Types

```ts
// réponse brute /v2/me (sous-ensemble utile) — dans src/lib/types.ts (préfixe Api42 / Ft42)
interface Ft42Me {
  id: number;
  login: string;
  image?: { link?: string | null } | null;
}

// forme normalisée interne
interface PlayerProfile {
  ftId: number;
  login: string;
  avatarUrl: string | null;
}

// DI de l'upsert
interface UpsertDeps {
  upsertPlayer(row: {
    ft_id: number;
    login: string;
    avatar_url: string | null;
  }): Promise<{ error: unknown }>;
}
```

`mapFt42Profile` extrait `avatarUrl` depuis `image.link` (null si absent).
L'implémentation réelle de `UpsertDeps.upsertPlayer` enrobe
`supabaseAdmin.from("users").upsert(row, { onConflict: "ft_id" })`.

## 5. Flux de données

1. User clique « Se connecter avec 42 » → server action `signIn("42")`.
2. Redirect OAuth vers `intra.42.fr` → retour sur `/api/auth/callback/42`.
3. NextAuth échange le code contre l'`access_token` **utilisateur**.
4. NextAuth lit `/v2/me` (userinfo du provider) avec ce token utilisateur.
5. `profile(raw)` → `mapFt42Profile` → objet normalisé.
6. Callback `signIn({ profile })` → `upsertPlayer(mapped, { supabaseAdmin… })`.
   - Succès → `return true`. Échec → throw → login refusé.
7. Callback `jwt` (premier login) → persiste `ftId/login/avatarUrl` dans le token.
8. Callback `session` → recopie vers `session.user`.
9. `<SiteHeader/>` lit `await auth()` → affiche avatar + login + bouton déconnexion.

## 6. Gestion d'erreurs

- **Upsert raté** : `signIn` callback throw → NextAuth refuse le login. Pas de
  session sans fiche `users` correspondante.
- **`/v2/me` via token utilisateur** : on **ne passe pas** par `fetch42()` (qui
  utilise le token applicatif `client_credentials`). C'est le seul appel API 42
  hors wrapper, assumé et documenté dans la skill `42api-fetch` (note ajoutée).
- **Secrets** : aucun token/secret loggé. `FT_API_SECRET` et `AUTH_SECRET`
  restent server-only (jamais dans un fichier `"use client"`).

## 7. Variables d'environnement

Déjà présentes dans `.env.local.example` : `FT_API_UID`, `FT_API_SECRET`,
`NEXTAUTH_URL`, `NEXTAUTH_SECRET`.

**À réconcilier** : NextAuth v5 attend par défaut `AUTH_SECRET` (et lit `AUTH_URL`).
Au moment de l'implémentation :
1. Vérifier dans `node_modules/next-auth/` le nom réellement attendu.
2. Si v5 exige `AUTH_SECRET`, mettre à jour `.env.local.example` (renommer
   `NEXTAUTH_SECRET` → `AUTH_SECRET`, garder un commentaire de continuité) plutôt
   que de forcer un alias dans le code.

## 8. Points à vérifier au build (Next 16 / NextAuth v5)

1. Nom de variable secret (`AUTH_SECRET` vs `NEXTAUTH_SECRET`) — cf. §7.
2. Existence et signature du provider built-in `42-school` dans
   `node_modules/next-auth/providers/42-school` ; sinon config OAuth manuelle
   (authorization/token/userinfo URLs intra.42.fr).
3. Compat App Router des server actions `signIn`/`signOut` (forme `<form action={…}>`).
4. `route.ts` : pas de `runtime = "edge"` (supabase-js + service_role = Node).

## 9. Stratégie de tests

| Cible | Cas |
|---|---|
| `mapFt42Profile` | (a) profil complet, (b) `image` absent, (c) `image.link` null. |
| `upsertPlayer` | (a) payload `{ ft_id, login, avatar_url }` correct passé au fake, (b) `deps.upsertPlayer` renvoie `{ error }` → `upsertPlayer` throw. |

NextAuth config, route handler et composants UI ne sont pas unit-testés
(territoire intégration) : couverts par `typecheck` + `build` + test manuel du
flux complet. Cohérent avec la brique sync (seul l'auth de la route avait un test).
